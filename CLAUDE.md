# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Stellarium is a decentralized API platform built on [RequestScript](https://www.npmjs.com/package/requestscript). Nodes share `Resources` with peers. Paid resource calls are paid from organizations' prepaid USD balances through a centralized operator, which pays providers out through Stripe Connect. All amounts are integer micro-USD (1 USD = 1,000,000). The move from Solana to Stripe is in progress: `programs/escrow_program` is unused and due for deletion. See `AGENTS.md` for Turborepo guidance: read the installed `turbo` package's bundled docs before changing turbo config.

## Commands

The repo is a pnpm monorepo (`apps/*`, `packages/*`) driven by Turborepo. `test` depends on `build`.

```sh
pnpm install
pnpm build          # turbo run build (tsc -> dist/)
pnpm test           # turbo run test (vitest)
pnpm lint           # turbo run lint (biome lint src; formatter disabled)
pnpm turbo run build test lint --continue   # everything, without stopping at the first failure

# Single package / single test
pnpm --filter stellarium-ts test
pnpm --filter stellarium-ts exec vitest run src/tests/resource/invoker.test.ts -t "payment voucher"
pnpm --filter stellarium-ts check-types
```

CI (`.github/workflows/ci.yml`) runs `pnpm build`, `pnpm check-types` and `pnpm test` on Node 20, plus `cargo test` for the (unused) escrow program. `check-types` must run after `build`: the operator type-checks against `stellarium-ts`'s `dist/` declarations. Lint is not part of CI, and the operator has pre-existing biome errors.

**Operator DB schema changes** (`apps/operator/src/db/schema.ts`) need a generated migration committed under `apps/operator/drizzle/`. The operator applies migrations itself at startup.
```sh
cd apps/operator && DATABASE_URL='postgresql://stellarium:local-only-password@127.0.0.1:5432/stellarium' pnpm exec drizzle-kit generate
```
When it is ambiguous whether a column was renamed or newly created, drizzle-kit stops with `missing_hints`. Re-run with `--hints '[...]'` as the output instructs.

**Full local stack** (Postgres, operator, two nodes, and the dashboard on port 3010): the README's "Running Locally" section, in three parts: paid calls on seeded credit, the dashboard with Clerk, and Stripe test mode end to end. The root `.env` holds the fixture nodes' public keys (`PROVIDER_SIGNING_PUBLIC_KEY`, `CALLER_SIGNING_PUBLIC_KEY`). The operator runs `seed:dev` (`apps/operator/src/seed.ts`) unless `SEED_DEV=0`, enrolling them in two organizations and crediting the caller. Each app's `.env` is baked into its image, so changing one needs `docker compose up -d --build <service>`. `docs/local-e2e.md` and the README's Payments sections still describe Solana.

## Architecture

### Components
- **`packages/stellarium-ts`**: the node library, published to npm. `StellariumNode` (`src/server.ts`) collects registered resources, resolves a `NodeConfig` from its options and then the environment (`resolveConfig`), opens the SQLite DB (`openDatabase` in `src/db/db.ts`; `requestscript.db` in the cwd by default, `:memory:` in tests), mounts `src/routes.ts` at `/v1` on a caller-supplied Fastify instance, and optionally bootstraps from a `startingPeer` (`src/startup.ts`). Dependencies are wired together in `src/service.ts`. Nothing reads `process.env` outside `resolveConfig`, so several nodes can run in one process. SQLite schema changes that `CREATE TABLE IF NOT EXISTS` can't apply bump `SCHEMA_VERSION` in `db.ts`, which rebuilds the learned-resource tables.
- **`apps/operator`**: a Fastify service on port 3001 backed by Postgres and Drizzle. **Organizations** (`organizations.ts`) own node keys (`nodes`; a key belongs to at most one organization), a prepaid balance and a payable balance. A node joins one with a one-time enrollment token through `POST /v1/nodes/session`, which it calls at startup. Node requests are signed (`auth/nodeAuth.ts`, a `preValidation` hook). `PaymentService` (`payments/`) moves money per voucher: `authorize` holds the voucher's amount (an inference voucher's `maxAmount`) on the payer organization's available balance (`balance − held`), `capture` charges it and credits the recipient's payable balance less the platform fee (`PLATFORM_FEE_BPS`, default 2000), and `release` frees it. Each is idempotent per voucher. Every balance change locks the organizations' rows (`lockOrganizations`, in id order) and writes balanced `ledger_entries` (`ledger.ts`) in the same transaction as the cached balances on `organizations`. A maintenance interval releases holds `HOLD_GRACE_MS` past their voucher's expiry. Authorization refuses an unenrolled payer (402), a revoked node or frozen organization (403), an organization paying itself or a recipient without `payoutsEnabled` (422), and an insufficient balance (402). Stripe (`stripe/gateway.ts`, an interface tests fake with `FakeStripe`) is optional: with `STRIPE_SECRET_KEY`, `BillingService` (`billing/`) creates Checkout top-ups, Customer Portal sessions and Connect Express accounts, `StripeWebhookService` (`stripe/webhooks.ts`, routes `/v1/stripe/webhook` and `/v1/stripe/connect-webhook` with raw-body signature checks) credits top-ups and debits refunds and disputes, and `PayoutService` (`payouts/`) claims a payout (debiting the payable balance) before sending its transfer with the payout id as idempotency key. Payouts pay what was captured more than `PAYOUT_HOLD_DAYS` ago, at most once per interval, in whole cents. With `CLERK_SECRET_KEY`, the dashboard API (`routes/dashboard.ts`, `/v1/org/...`) authenticates Clerk session tokens (`auth/clerk.ts`, v1 and v2 org claims) and creates an organization per Clerk organization on first use. Clerk `admin`s move money and manage nodes; members read.
- **`apps/dashboard`**: the console at platform.stellarium.sh (Next.js App Router, Clerk, CSS Modules, no Tailwind; look and tokens from stellarium.sh, layout after the Claude Console). Server components fetch through `lib/api.ts` (`server-only`) with the user's Clerk session token; mutations are Server Actions in `lib/actions.ts`. `proxy.ts` is Next 16's middleware. Read `node_modules/next/dist/docs/` before writing Next code (`AGENTS.md`). See `apps/dashboard/README.md`.
- **`apps/local-caller-node` / `apps/local-resource-node`**: fixture nodes for local end-to-end runs. The resource node hosts a paid `com.example.Weather.temperature`. They depend on the workspace package (`"stellarium-ts": "workspace:*"`), which resolves to `packages/stellarium-ts/dist`. Rebuild the package (`pnpm --filter stellarium-ts build`) for changes to reach them. `docker compose up --build` does this already.

### Request flow
1. `POST /v1/run` parses a RequestScript `request` and runs it with `interpretParsed`, using the node's `CombinationResourceResolver` and `CombinationResourceInvoker` (`src/resource/`).
2. The invoker runs local resources in-process (`exec`). A resource with `metadata.baseUrl` (learned from a peer) is forwarded instead: the invoker POSTs `{resourcePath, resourceName, functionName, parameters}` to `{baseUrl}/v1/run/resource`, with retry and exponential backoff.
3. If the remote function is `restricted`, the caller attaches an authorization built from a held grant chain rooted at the provider (`GrantService.chainFor`). Without one, it fails before any network call.
4. If the remote function has a `paymentManifest`, the caller attaches a signed `PaymentVoucher` paying the manifest's `recipientOrganizationId`. A provider node learns its organization from the operator at startup (`StellariumNode.start` → `OperatorClient.session`, enrolling with `ENROLLMENT_TOKEN` the first time) and stamps it on its paid functions' manifests (`ResourceRepository.getInternalResources`); resource authors don't set it. The voucher's `costMicroUsd` is checked against the invoker's cost limit (`costLimitMicroUsd`) first. An inference function (`kind: 'inference'`, `src/resource/inference.ts`) is priced per million tokens instead. The caller first POSTs the call to `{baseUrl}/v1/run/resource/estimate`, which runs the provider's `estimateInputTokens` and answers `{ inputTokens, maxAmount }`. It checks `maxAmount` against the rates and `inferenceCostLimitMicroUsd`, then signs an `InferencePaymentVoucher` for `maxAmount`, the rates and the call's `maxTokens`. The provider re-runs the estimator and answers 402 if `maxAmount` doesn't cover it. The provider's `/run/resource` requires a voucher for a paid function (402 without one) and checks its invocation hash, amount ≥ cost, recipient (its own organization), expiry and signature against the function's own manifest. It then calls `OperatorClient.authorize` and answers the operator's refusal status (503 if unreachable) without running the function. After the invoke it captures, or releases the hold for an error or a free inference call, fire-and-forget in a `setTimeout`. An inference capture sends `{ voucher, usage }`, with the usage its `exec` returned and output capped at `maxTokens`, and the operator charges the usage at the signed rates, capped at the hold.

### Signing and voucher invariants
- Keys are Ed25519: the public key is SPKI DER and the private key is PKCS#8 DER, both base64url (`SIGNING_PUBLIC_KEY`/`SIGNING_PRIVATE_KEY`).
- Node requests to the operator carry `Authorization: Stellarium <base64url JSON { publicKey, timestamp, signature }>`, signed over `operatorRequestPayload` (`{ method, path, bodyHash, timestamp }`, `src/client/operatorAuth.ts`, copied in `apps/operator/src/auth/nodeAuth.ts`). The operator accepts timestamps within five minutes and has no nonce store, so every node endpoint must stay idempotent.
- `signData`, `verifyData` and `hashData` (`src/crypto/utils.ts`) operate on `JSON.stringify` output, not canonical JSON. **Key insertion order is part of the signed or hashed bytes.**
- The voucher carries `invocationHash`: the hash of `{resourcePath, resourceName, functionName, parameters}`, built by `invocationHash()` in `src/resource/invoker.ts`. The signature covers `paymentVoucherPayload(voucher)`, meaning every voucher field except `signature`, in a fixed order. The provider recomputes the hash from the incoming request. The operator receives only `{ voucher }`.
- Inference vouchers are signed over `inferenceVoucherPayload(voucher)`, which leads with `kind: 'inference'` and has `maxAmount`, both rates and `maxTokens` instead of `amount`. The charge formula (`inferenceCharge`) is copied in `apps/operator/src/inference.ts`.
- The voucher wire format is duplicated in places that must stay in sync: `PaymentVoucher` and `InferencePaymentVoucher` in `packages/stellarium-ts/src/resource/invoker.ts`, `PaymentSubmission` in `packages/stellarium-ts/src/client/operatorClient.ts`, and the types, payload and route schemas in `apps/operator/src/payments/types.ts`, `apps/operator/src/routes/payments.ts` and `apps/operator/src/testing.ts`. `apps/operator/src/payments/paymentService.test.ts` verifies vouchers made by the real `CombinationResourceInvoker`, and `apps/operator/src/e2e.test.ts` runs real nodes against the operator over HTTP, so drift fails the tests.
- Grants (`src/grant/`) are signed over `grantPayload` (every field except `signature`) and linked by `grantHash`. A call to a restricted function carries an `InvocationAuthorization` signed over `invocationAuthorizationPayload` (`{ invocationHash, publicKey, nonce, expiresAt, grantsHash }`). The provider checks it before the voucher, and refuses a nonce it has already seen (kept in the `seen_nonce` table), so the invoker signs a new authorization on each retry while reusing the voucher. Renewal requests are signed over `grantRenewalPayload`, and grant requests (`POST /v1/grants/request`, decided by the node's `approveGrant` hook) over `grantRequestPayload`, which signs omitted `details` as `null`. Verifiers accept expiries up to `CLOCK_SKEW_TOLERANCE_MS` past each lifetime cap. Held chains are keyed by their leaf's `(issuer, id)`, since issuers pick their own ids. Keys blocked through `/v1/admin/blocked-callers` are refused in any chain audience, in renewals and requests, and as a voucher's `publicKey`. The `/v1/admin` routes share `/v1/run`'s `requireApiKey` hook.
- Peer announcements are signed over `peerAnnouncementPayload` (`{ baseUrl, name, publicKey, expiry }`) and verified with the announced key. Resource broadcasts are signed over `resourceAnnouncementPayload` (`{ resources, expiry }`) and carry the sender's `publicKey`. Both expiries must be within `MAX_SIGNATURE_LIFETIME_MS` (one hour). A peer may only publish resources served from its own base URL that no other peer owns.

### Conventions
- ESM throughout. Relative imports use `.js` extensions.
- `dist/` directories are build output. Don't edit them by hand.
- Tests live in `packages/stellarium-ts/src/tests/` (mirroring `src/`, shared fixtures in `tests/helpers.ts`, a two-node HTTP test in `tests/integration/`) and as `*.test.ts` files next to the source in the operator. Operator DB tests use in-memory PGlite with the committed migrations (`src/testing.ts`), so no Postgres is needed. Operator services take the `Database` type from `src/db/database.ts`, which both node-postgres and PGlite satisfy.
