# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Stellarium is a decentralized API platform built on [RequestScript](https://www.npmjs.com/package/requestscript). Nodes share `Resources` with peers. Paid resource calls are paid from organizations' prepaid USD balances through a centralized operator, which pays providers out through Stripe Connect. All amounts are integer micro-USD (1 USD = 1,000,000). See `AGENTS.md` for Turborepo guidance: read the installed `turbo` package's bundled docs before changing turbo config.

## Commands

The repo is a pnpm monorepo (`apps/*`, `packages/*`) driven by Turborepo. `test` depends on `build`.

```sh
pnpm install
pnpm build          # turbo run build (tsc -> dist/)
pnpm test           # turbo run test (vitest)
pnpm lint           # turbo run lint (biome lint src; formatter disabled)
pnpm turbo run build test lint --continue   # everything, without stopping at the first failure

# Single package / single test
pnpm --filter stellarium-ts test
pnpm --filter stellarium-ts exec vitest run src/tests/resource/invoker.test.ts -t "payment voucher"
pnpm --filter stellarium-ts check-types
```

CI (`.github/workflows/ci.yml`) runs `pnpm build`, `pnpm check-types` and `pnpm test` on Node 20. `check-types` must run after `build`: the operator type-checks against `stellarium-ts`'s `dist/` declarations. Lint is not part of CI, and the operator has pre-existing biome errors.

**Operator DB schema changes** (`apps/operator/src/db/schema.ts`) need a generated migration committed under `apps/operator/drizzle/`. The operator applies migrations itself at startup.
```sh
cd apps/operator && DATABASE_URL='postgresql://stellarium:local-only-password@127.0.0.1:5432/stellarium' pnpm exec drizzle-kit generate
```
When it is ambiguous whether a column was renamed or newly created, drizzle-kit stops with `missing_hints`. Re-run with `--hints '[...]'` as the output instructs.

**Full local stack** (Postgres, operator, two nodes, and the dashboard on port 3010): the README's "Running Locally" section, in three parts: paid calls on seeded credit, the dashboard, and Stripe test mode end to end. The root `.env` holds the fixture nodes' public keys (`PROVIDER_SIGNING_PUBLIC_KEY`, `CALLER_SIGNING_PUBLIC_KEY`). The operator runs `seed:dev` (`apps/operator/src/seed.ts`) unless `SEED_DEV=0`, enrolling them in two organizations and crediting the caller. It also lists the resource node and gives the caller's organization an API client for it (`cli_local_caller`). Each app's `.env` is baked into its image, so changing one needs `docker compose up -d --build <service>`. Without `RESEND_API_KEY` the operator logs verification and invitation emails instead of sending them (`docker compose logs operator | grep Email`). Production setup (live Stripe, Resend, webhook endpoints) is in `docs/production-deploy.md`.

## Architecture

### Components
- **`packages/stellarium-ts`**: the node library, published to npm. `StellariumNode` (`src/server.ts`) collects registered resources, resolves a `NodeConfig` from its options and then the environment (`resolveConfig`), opens its database (`openDatabase` in `src/db/db.ts`), mounts `src/routes.ts` at `/v1` on a caller-supplied Fastify instance, and optionally bootstraps from a `startingPeer` (`src/startup.ts`). Dependencies are wired together in `src/service.ts`. Nothing reads `process.env` outside `resolveConfig`, so several nodes can run in one process. The database is SQLite (`requestscript.db` in the cwd by default, `:memory:` in tests) or, with `DATABASE_URL`, Postgres, optionally in its own `DATABASE_SCHEMA`. Repositories take a `NodeDatabase` (`src/db/database.ts`; `src/db/sqlite.ts`, `src/db/postgres.ts`) and write raw SQL both accept: `?` placeholders (rewritten to `$n` for Postgres), `ON CONFLICT` rather than `INSERT OR IGNORE`, `RETURNING id` rather than a last insert id, and an explicit `ORDER BY` wherever order matters. Inside `db.transaction(tx => …)`, query through `tx` only: PGlite has one connection, so a query through the database deadlocks. Tables are declared once in `db.ts`, with `${t.id}` and `${t.bigint}` for the column types that differ. Schema changes that `CREATE TABLE IF NOT EXISTS` can't apply bump `SCHEMA_VERSION` in `db.ts`, which rebuilds the learned-resource tables (kept in `PRAGMA user_version` on SQLite and the `stellarium_schema` table on Postgres).
- **`apps/operator`**: a Fastify service on port 3001 backed by Postgres and Drizzle. **Organizations** (`organizations.ts`) own node keys (`nodes`; a key belongs to at most one organization), a prepaid balance and a payable balance. A node joins one with a one-time enrollment token through `POST /v1/nodes/session`, which it calls at startup. Node requests are signed (`auth/nodeAuth.ts`, a `preValidation` hook). A node's row also holds its listing: the `baseUrl` it reports in its session, a name, a price per million script tokens and `listed`. Listing fetches `{baseUrl}/v1/self` to check the key. `ApiClientService` and `RunService` (`runs/`) handle API clients, run tokens (`RunTokenSigner`, keyed by `RUN_TOKEN_PRIVATE_KEY`) and billed runs (`runs`, whose hold also pays the run's calls). `PaymentService` (`payments/`) moves money per voucher: `authorize` holds the voucher's amount (an inference voucher's `maxAmount`) on the payer organization's available balance (`balance − held`), `capture` charges it and credits the recipient's payable balance less the platform fee (`PLATFORM_FEE_BPS`, default 2000), and `release` frees it. Each is idempotent per voucher. Every balance change locks the organizations' rows (`lockOrganizations`, in id order) and writes balanced `ledger_entries` (`ledger.ts`) in the same transaction as the cached balances on `organizations`. A maintenance interval releases holds `HOLD_GRACE_MS` past their voucher's expiry. Authorization refuses an unenrolled payer (402), a revoked node or frozen organization (403), an organization paying itself or a recipient without `payoutsEnabled` (422), and an insufficient balance (402). Stripe (`stripe/gateway.ts`, an interface tests fake with `FakeStripe`) is optional: with `STRIPE_SECRET_KEY`, `BillingService` (`billing/`) creates Checkout top-ups, Customer Portal sessions and Connect Express accounts, `StripeWebhookService` (`stripe/webhooks.ts`, routes `/v1/stripe/webhook` and `/v1/stripe/connect-webhook` with raw-body signature checks) credits top-ups and debits refunds and disputes, and `PayoutService` (`payouts/`) claims a payout (debiting the payable balance) before sending its transfer with the payout id as idempotency key. Payouts pay what was captured more than `PAYOUT_HOLD_DAYS` ago, at most once per interval, in whole cents. With `BETTER_AUTH_SECRET`, the operator hosts [Better Auth](https://www.better-auth.com) (`auth/betterAuth.ts`: email and password, optional GitHub, the organization plugin) at `/v1/auth/*` (`routes/auth.ts`), with its `auth_*` tables in the operator's schema. Emails go through Resend or, without `RESEND_API_KEY`, to the log (`auth/email.ts`). The dashboard API (`routes/dashboard.ts`, `/v1/org/...`) reads the Better Auth session cookie the dashboard forwards (`auth/dashboardAuth.ts`) and creates an operator organization per Better Auth organization on first use (`organizations.authOrganizationId`). Owners and admins move money and manage nodes; members read.
- **`apps/dashboard`**: the console at platform.stellarium.sh (Next.js App Router, CSS Modules, no Tailwind; look and tokens from stellarium.sh, layout after the Claude Console). `app/api/auth/[...all]/route.ts` forwards `/api/auth/*` to the operator's Better Auth, so session cookies are the dashboard's; client components use `lib/auth-client.ts`. Server components fetch through `lib/api.ts` (`server-only`), forwarding the session cookie; mutations are Server Actions in `lib/actions.ts`. `proxy.ts` is Next 16's middleware. Read `node_modules/next/dist/docs/` before writing Next code (`AGENTS.md`). See `apps/dashboard/README.md`.
- **`apps/local-caller-node` / `apps/local-resource-node`**: fixture nodes for local end-to-end runs. The resource node hosts a paid `com.example.Weather.temperature`. They depend on the workspace package (`"stellarium-ts": "workspace:*"`), which resolves to `packages/stellarium-ts/dist`. Rebuild the package (`pnpm --filter stellarium-ts build`) for changes to reach them. `docker compose up --build` does this already.

### Request flow
1. `POST /v1/run` parses a RequestScript `request` and runs it with `interpretParsed`, using the node's `CombinationResourceResolver` and `CombinationResourceInvoker` (`src/resource/`).
2. The invoker runs local resources in-process (`exec`). A resource with `metadata.baseUrl` (learned from a peer) is forwarded instead: the invoker POSTs `{resourcePath, resourceName, functionName, parameters}` to `{baseUrl}/v1/run/resource`, with retry and exponential backoff.
3. If the remote function is `restricted`, the caller attaches an authorization built from a held grant chain rooted at the provider (`GrantService.chainFor`). Without one, it fails before any network call.
4. If the remote function has a `paymentManifest`, the caller attaches a signed `PaymentVoucher` paying the manifest's `recipientOrganizationId`. A provider node learns its organization from the operator at startup (`StellariumNode.start` → `OperatorClient.session`, enrolling with `ENROLLMENT_TOKEN` the first time) and stamps it on its paid functions' manifests (`ResourceRepository.getInternalResources`); resource authors don't set it. The voucher's `costMicroUsd` is checked against the invoker's cost limit (`costLimitMicroUsd`) first. An inference function (`kind: 'inference'`, `src/resource/inference.ts`) is priced per million tokens instead. The caller first POSTs the call to `{baseUrl}/v1/run/resource/estimate`, which runs the provider's `estimateInputTokens` and answers `{ inputTokens, maxAmount }`. It checks `maxAmount` against the rates and `inferenceCostLimitMicroUsd`, then signs an `InferencePaymentVoucher` for `maxAmount`, the rates and the call's `maxTokens`. The provider re-runs the estimator and answers 402 if `maxAmount` doesn't cover it. The provider's `/run/resource` requires a voucher for a paid function (402 without one) and checks its invocation hash, amount ≥ cost, recipient (its own organization), expiry and signature against the function's own manifest. It then authorizes, invokes and settles through `settlePaidCall` (`src/resource/settlement.ts`): it calls `OperatorClient.authorize` and answers the operator's refusal status (503 if unreachable) without running the function. After the invoke it captures, or releases the hold for an error or a free inference call, fire-and-forget in a `setTimeout`. An inference capture sends `{ voucher, usage }`, with the usage its `exec` returned and output capped at `maxTokens`, and the operator charges the usage at the signed rates, capped at the hold.
5. `/v1/run` accepts the node's `API_KEY` or a **run token**: an EdDSA JWT an organization's API client gets from the operator's `POST /v1/oauth/token` (`apps/operator/src/runs/`). Its `aud` is the node's public key, and `org` is the paying organization. The node verifies it against the operator's `/.well-known/jwks.json` (`RunTokenVerifier`, `src/client/runTokens.ts`). API-key runs and runs by the node's own organization are free, as before. Any other run is billed:
   - The node first calls `OperatorClient.authorizeRun` with the token, a run id it picks and the source. The operator computes the script's `maxTokens` itself and holds up to the client's `maxRunCostMicroUsd`.
   - The script runs with `resourceInvoker.forRun({ runId })`. Each of its paid calls, remote or to this node's own paid functions (`invokeLocalPaid`), signs a voucher carrying the `runId`, and the operator moves the voucher's amount from the run's hold to its receipt. The per-call cost limits don't apply.
   - The script gets the verified run token's payload as the read-only built-in variable `jwt` (requestscript ≥ 1.3.0's `builtins` option), or `null` for an API-key run.
   - A `TokenMeter` (requestscript ≥ 1.2.0) counts the tokens executed. The node captures them with `captureRun`, charged at the node's listed price per million tokens. A script that fails with a `RequestScriptError` answers 422 and is still captured. Any other failure releases the run.
6. **Contracts** (`src/contract/`): RequestScript contracts deployed with `POST /v1/contracts` (the API key, or a run token, whose organization then owns every version; another organization pays `contractDeployFeeMicroUsd` through a fixed voucher on its run). They need a path and a return type (requestscript ≥ 1.4.0). Versions are immutable, and the latest version of each is one of the node's resources (`ResourceRepository`'s `ContractSource`), with one function, `run`, `kind: 'contract'`, priced at the node's listed price (`priceMicroUsdPerMillionTokens`, from the operator's session, refreshed every five minutes). A contract's paid calls are always paid by its caller:
   - A remote caller signs a `ContractPaymentVoucher` for `maxAmount` (`contractCostLimitMicroUsd`) and sends `contractDepth`. The provider checks it, then `OperatorClient.authorizeContractRun` asks the operator (`RunService.authorizeContract`) to hold a run whose id is the voucher's `invocationId`, on the signer's organization, or out of the parent run's hold when the voucher carries a `runId`. The operator answers `free` when the payer is the node's own organization. `ContractService.serve` runs the contract with `resourceInvoker.forScript({ runId })` and captures its tokens.
   - On the same node, `CombinationResourceInvoker` hands contracts to its `ContractHost` (`ContractService.invokeLocal`): free from an unbilled script, and from a billed run through the same child-run path. Invokers carry a `ScriptContext` (`runId`, `jwt`, `depth`). Contracts nest at most `MAX_CONTRACT_DEPTH` (8) deep.
   - When a child run settles or expires, its unused hold goes back to the parent run if that is still held, and to the payer otherwise (`RunService.returnHold`).

### Signing and voucher invariants
- Keys are Ed25519: the public key is SPKI DER and the private key is PKCS#8 DER, both base64url (`SIGNING_PUBLIC_KEY`/`SIGNING_PRIVATE_KEY`).
- Node requests to the operator carry `Authorization: Stellarium <base64url JSON { publicKey, timestamp, signature }>`, signed over `operatorRequestPayload` (`{ method, path, bodyHash, timestamp }`, `src/client/operatorAuth.ts`, copied in `apps/operator/src/auth/nodeAuth.ts`). The operator accepts timestamps within five minutes and has no nonce store, so every node endpoint must stay idempotent.
- `signData`, `verifyData` and `hashData` (`src/crypto/utils.ts`) operate on `JSON.stringify` output, not canonical JSON. **Key insertion order is part of the signed or hashed bytes.**
- The voucher carries `invocationHash`: the hash of `{resourcePath, resourceName, functionName, parameters}`, built by `invocationHash()` in `src/resource/invoker.ts`. The signature covers `paymentVoucherPayload(voucher)`, meaning every voucher field except `signature`, in a fixed order. The provider recomputes the hash from the incoming request. The operator receives only `{ voucher }`.
- A voucher's optional `runId` is signed last, and only when set (`runPayload`), so vouchers without one sign the same bytes as before it existed. The operator accepts a run's voucher only when it is signed by the run's node.
- Contract vouchers are signed over `contractVoucherPayload(voucher)`: `kind: 'contract'` first, then `maxAmount` and `priceMicroUsdPerMillionTokens`, with `runId` last as for the others. They authorize a run, not a payment, so the operator copy is `ContractVoucher` and `contractVoucherPayload` in `apps/operator/src/payments/types.ts`, used by `RunService`.
- Inference vouchers are signed over `inferenceVoucherPayload(voucher)`, which leads with `kind: 'inference'` and has `maxAmount`, both rates and `maxTokens` instead of `amount`. The charge formula (`inferenceCharge`) is copied in `apps/operator/src/inference.ts`.
- The voucher wire format is duplicated in places that must stay in sync: `PaymentVoucher`, `InferencePaymentVoucher` and `ContractPaymentVoucher` in `packages/stellarium-ts/src/resource/invoker.ts`, `PaymentSubmission` in `packages/stellarium-ts/src/client/operatorClient.ts`, and the types, payload and route schemas in `apps/operator/src/payments/types.ts`, `apps/operator/src/routes/payments.ts`, `apps/operator/src/routes/runs.ts` (contract vouchers) and `apps/operator/src/testing.ts`, and the voucher schemas in `packages/stellarium-ts/src/routes.ts`. `apps/operator/src/payments/paymentService.test.ts` verifies vouchers made by the real `CombinationResourceInvoker`, and `apps/operator/src/e2e.test.ts` runs real nodes against the operator over HTTP, so drift fails the tests.
- Grants (`src/grant/`) are signed over `grantPayload` (every field except `signature`) and linked by `grantHash`. A call to a restricted function carries an `InvocationAuthorization` signed over `invocationAuthorizationPayload` (`{ invocationHash, publicKey, nonce, expiresAt, grantsHash }`). The provider checks it before the voucher, and refuses a nonce it has already seen (kept in the `seen_nonce` table), so the invoker signs a new authorization on each retry while reusing the voucher. Renewal requests are signed over `grantRenewalPayload`, and grant requests (`POST /v1/grants/request`, decided by the node's `approveGrant` hook) over `grantRequestPayload`, which signs omitted `details` as `null`. Verifiers accept expiries up to `CLOCK_SKEW_TOLERANCE_MS` past each lifetime cap. Held chains are keyed by their leaf's `(issuer, id)`, since issuers pick their own ids. Keys blocked through `/v1/admin/blocked-callers` are refused in any chain audience, in renewals and requests, and as a voucher's `publicKey`. The `/v1/admin` routes share `/v1/run`'s `requireApiKey` hook.
- Peer announcements are signed over `peerAnnouncementPayload` (`{ baseUrl, name, publicKey, expiry }`) and verified with the announced key. Resource broadcasts are signed over `resourceAnnouncementPayload` (`{ resources, expiry }`) and carry the sender's `publicKey`. Both expiries must be within `MAX_SIGNATURE_LIFETIME_MS` (one hour). A peer may only publish resources served from its own base URL that no other peer owns.

### Conventions
- ESM throughout. Relative imports use `.js` extensions.
- `dist/` directories are build output. Don't edit them by hand.
- Tests live in `packages/stellarium-ts/src/tests/` (mirroring `src/`, shared fixtures in `tests/helpers.ts`, a two-node HTTP test in `tests/integration/`) and as `*.test.ts` files next to the source in the operator. The node's database-backed suites run against SQLite and Postgres: `describe.each(DIALECTS)` with `openTestDatabase(dialect)`, which uses in-memory PGlite (hence the 30-second timeouts in its `vitest.config.ts`). Operator DB tests use in-memory PGlite with the committed migrations (`src/testing.ts`), so no Postgres is needed. Operator services take the `Database` type from `src/db/database.ts`, which both node-postgres and PGlite satisfy.
